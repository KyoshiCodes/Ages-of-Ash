# Recovery and backup ownership

**Owner:** the on-call release operator owns backup checks, restore approval, incident timeline, and final traffic cutover. A second operator reviews any production cutover. These roles must be assigned before launch; this document does not claim a measured recovery time.

The daily `ages-backup.timer` invokes `deploy/backup.mjs` as the `ages` service user with a dedicated `ages_backup` PostgreSQL role (`pg_read_all_data`, no write privilege), writes a PostgreSQL custom-format dump to `/var/backups/ages` through a temporary file, sets restrictive file permissions, and keeps seven local files. The operator must copy each verified dump to an encrypted off-host store. Local retention alone does not survive instance or volume loss. Check `sudo systemctl list-timers ages-backup.timer`, `sudo systemctl status ages-backup`, file timestamps/sizes, and journal errors daily. Never commit a dump, database URL, `.env`, or restore transcript containing credentials.

For a rehearsal, use a **non-production PostgreSQL server** and a new empty database whose name starts `ages_restore_`. Provision a role with restore rights and set DATABASE_URL privately for that target. Copy a recent dump to the rehearsal host. Run `node deploy/restore.mjs /absolute/path/to/backup.dump --confirm-empty-target`. The script rejects production NODE_ENV, a differently named target, and any target with application tables. It uses `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`. Then run `pnpm run doctor` against that target and inspect migration/content status, account and player counts, a sampled player aggregate, session/auth behavior, canonical content and world boss. Attempting a second restore into the same populated target must fail. The native Windows `pnpm verify:full` path performs this isolated dump/restore/refusal comparison automatically against its generated test cluster using a separate read-only backup role; it also confirms that role has no Player insert privilege. Hosted CI has a fresh PostgreSQL service but skips the native binary restore drill.

If production data is damaged, stop API/worker writes and collect the incident timeline. Determine the last trustworthy backup and measure its age. Restore to a separate database/server, run checks and a smoke test, then approve and document cutover. Changing the symlink to older code does not reverse a migration or recover data. If a schema change is irreversible, replaying a prior code release against it can corrupt saves; restore and migrate forward under operator review. Keep the source database read-only until the cause is understood. Rotate any credentials exposed during incident handling.

Recovery targets are provisional: daily backup implies up to 24 hours of potential loss before off-host copy; actual RPO/RTO must be measured in a hosted rehearsal. The on-call operator records backup timestamp, dump checksum, restore duration, consistency checks, cutover decision, and post-cutover auth/operation/worker/WebSocket checks.
