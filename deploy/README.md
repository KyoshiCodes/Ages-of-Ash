# Oracle Ampere release runbook

Status: design and scripts audited locally; **no OCI deployment has been executed here**. Use Ubuntu 24.04 ARM64, a reserved public address, DNS A record, PostgreSQL 18, Node 24, Caddy, and five separate identities: bootstrap administrator, migration owner, API runtime, worker runtime, read-only backup. The API and worker connect only to PostgreSQL on localhost. Caddy alone accepts public 80/443; API 3000, worker 3001, and database 5432 stay private.

## First provision

1. In OCI, allow TCP 80/443 in the instance VCN security list or NSG. Limit SSH to the operator address. The instance's local INPUT firewall is a second gate: `deploy/provision.mjs` inserts 80/443 before the reject rule and saves them using `iptables-persistent`. Check both gates. Do not publish an AAAA record until IPv6 routing and both firewalls are configured.
2. SSH from Windows: `ssh ubuntu@YOUR_IP`. Install initial Node to run the provisioner: `sudo apt-get update` and `sudo apt-get install -y nodejs git`. Clone the canonical repository and run `sudo node deploy/provision.mjs game.example.com`. This installs signed Node 24, PostgreSQL 18, Caddy, service units and pnpm. Review the package source keys and unit files before first run. Repeat execution retains existing environment files.
3. As the bootstrap database administrator, create four separate SCRAM login roles with generated passwords: `ages_migrator`, `ages_api`, `ages_worker`, `ages_backup`. In `sudo -u postgres psql`, run `CREATE ROLE ages_migrator LOGIN;` and likewise for the other three, then use `\password ages_migrator` (and each other role) to enter secrets without putting them in history; then `CREATE DATABASE ages OWNER ages_migrator;`. Connect to ages and run `REVOKE CONNECT ON DATABASE ages FROM PUBLIC;` and `CREATE SCHEMA pgboss AUTHORIZATION ages_worker;`, `GRANT CONNECT ON DATABASE ages TO ages_backup;`, and `GRANT pg_read_all_data TO ages_backup;`. The backup role reads all schemas for a complete `pg_dump` but has no game write privilege. Use private, unique passwords and do not put them in shell history. PostgreSQL listens on loopback only. The bootstrap account is never placed in a service environment.
4. Use `sudoedit` to set `/etc/ages/ages.env` to the API role URL plus `APP_ORIGIN=https://game.example.com`, `NODE_ENV=production`, `HOST=127.0.0.1`, `PORT=3000`, `ANALYTICS_ENABLED=false`, and a random `OPS_TOKEN` of at least 32 characters. Set `/etc/ages/worker.env` to `DATABASE_URL=` for the worker role plus `WORKER_PORT=3001`. Set `/etc/ages/migrate.env` to the migration role's `DATABASE_URL=`. Set `/etc/ages/backup.env` to the read-only backup role's `DATABASE_URL=`. URL-encode password characters. Create `ages.env`, `worker.env`, and `backup.env` as root with mode 0640 and owner `root:ages`. Create `migrate.env` with mode 0600 and owner `root:root`; the root release process reads it and passes the credential only to gated migration, grant and seed subprocesses. The shared runtime Unix user can read the three runtime files; split Unix identities during a later hardening pass. Keep bootstrap credentials outside all four files. In production the API validates HTTPS origin, loopback bind, token strength, and absence of admin URLs.
5. Confirm the exact commit passed the GitHub `CI` workflow and inspect every migration SQL file, the latest backup and backward compatibility before approval. Run `sudo node deploy/release.mjs --commit=<40-character-reviewed-SHA>` to fetch, install, generate and build in an immutable worktree. This preparation performs **no database migration, seed or service switch**. Then run the same command with `--approve-migrations`. That gated step runs `prisma migrate deploy` as `ages_migrator`, applies `deploy/database-grants.sql`, pauses old services, seeds with the migrator, prepares pg-boss queues as `ages_worker`, swaps the symlink and restarts services. It waits for `/api/ready`, which requires database, migration, canonical content, world boss, and a fresh worker heartbeat. There is a short service pause; persistent WebSockets reconnect from authoritative state.
6. Check `https://game.example.com/api/live` and `/api/ready` through Caddy, register a test account, perform an operation, and confirm worker jobs, WebSocket reconnect and a fresh backup. Caddy blocks `/internal/*` publicly; inspect operator metrics only on loopback with `Authorization: Bearer $OPS_TOKEN`, for example from the instance `curl -H 'Authorization: Bearer ...' http://127.0.0.1:3000/internal/metrics`. Never paste the token into shared logs or tickets. Run `sudo systemctl status ages-api ages-worker ages-backup.timer caddy` and `sudo journalctl -u ages-api -u ages-worker --since today`.

The Windows command wrapper is `./deploy/deploy.ps1 -RemoteHost ubuntu@YOUR_IP -Commit <reviewed SHA>`; it defaults to preparation. `-ApproveMigrations` crosses the same explicit gate. Restrict operator access and review the actual SHA shown by CI. `deploy/release.mjs` does not silently choose the latest branch head.

## CI backup/restore rehearsal

The Release foundation workflow uses an ephemeral PostgreSQL 18.6 service, its configured verification administrator, and PostgreSQL 18.6 client binaries from the signed PGDG noble source (package postgresql-client-18=18.6-1.pgdg24.04+2). The runner requires pg_dump, pg_restore and psql from /usr/lib/postgresql/18/bin; its database create/drop operations use the scoped administrator connection rather than the client commands. pnpm verify:full checks client/server major parity, creates random disposable roles and databases, verifies backup-role read-only and runtime-role privilege boundaries, dumps/restores/refuses a populated target, and compares the restored schema and representative data. The dump stays in ignored .local and is deleted even after a failed check; uploaded artifacts contain only sanitized stage logs, Playwright reports and safe diagnostics. Release foundation run 35798015112 passed the hosted dump/restore/refusal and full acceptance checks. A green CI run is not an OCI restore rehearsal. On OCI staging, an operator must rehearse off-host retrieval, decryption, empty-target restore, application checks and a timed cutover under the recovery owner in RECOVERY.md.

## Failure and rollback

If the readiness check fails, inspect the units, migration history, and structured logs. An optional code rollback flag restores the prior symlink **only when the applied schema and seed remain backward compatible**. Schema/data are never reversed by changing the symlink. For an irreversible migration, stop writes, restore a verified backup into a separate database, validate it, and execute the incident plan under the recovery owner. Never run `prisma migrate reset` or `db push` on production. Document the exact cutover and data-loss decision before repointing services. Refer to [RECOVERY.md](../docs/RECOVERY.md).

## Monitoring and capacity

`/api/live` is liveness; `/api/ready` includes database and worker freshness. The worker's loopback `/ready` and `/metrics` report job heartbeat/failure/retry/lag; the API metrics report HTTP error/latency, WebSocket health, database state and queue signals without tokens, URLs, request bodies or player state. Alert on readiness loss, stale worker heartbeat, repeated job failures, rising lag or retries, and unavailable backups. Start with a 60-second scrape and page for readiness failure beyond two checks; tune thresholds from real load. Use `journalctl -u ages-api -u ages-worker` for JSON lines and restrict journal readers. Set journald `SystemMaxUse=200M` if disk is tight. Backups run daily and retain seven local copies; copy encrypted dumps off-host and rehearse restore. Actual RPO/RTO and ARM64 performance remain unverified.

ARM64 dependency risk: argon2 native binaries, Prisma engine, Rolldown, Tailwind oxide and esbuild must resolve for aarch64. Build on the host with 2 GB free RAM. Record failures rather than copying Windows `node_modules`. Provisioning/branch protection/TLS/native modules/physical-device timing require an operator on the actual tenancy.

## Retention analytics

Collection is disabled by default. To enable it for a real player cohort, an operator sets `ANALYTICS_ENABLED=true` in the API environment after updating the privacy notice and recording the decision. Events contain action category, timings and counts; no email, chat, token, IP or full player state is stored in telemetry. On the host, run the aggregate report only with `ANALYTICS_ENABLED=true pnpm analytics --operator` from a restricted operator session; it prints cohort counts, median time to prestige, session length, operations per session and drop-off category, without player IDs. Restrict output to operators and avoid publishing very small cohorts. The intended session/telemetry retention is 30 days. `pnpm exec tsx scripts/retention-cleanup.ts` prints only an eligible count; any deletion requires a separately reviewed explicit `--confirm-delete` action. Never delete Audit or Receipt as part of analytics retention. The worker does not perform this cleanup automatically.
