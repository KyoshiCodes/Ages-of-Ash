# OCI deployment assets — staging preparation

Status: scripts and documentation are prepared; **no OCI staging host, DNS, IAM identity, bucket, key, alert or recovery cutover has been executed here**. Start with [the staging architecture](../docs/OCI_STAGING_ARCHITECTURE.md), [operator runbook](../docs/OCI_STAGING_RUNBOOK.md), [intake](../docs/STAGING_INTAKE_TEMPLATE.md) and [ownership template](../docs/RECOVERY_OWNERSHIP_TEMPLATE.md). The checked-in host provisioner is gated by `--approve-host-provisioning` and accepts a staging hostname only. It does not create OCI resources. The reviewed operator, not this repository, approves tenancy/network/shape/costs and executes any OCI changes.

The recommended first rehearsal is one Ubuntu 24.04 VM (ARM64 A1 if quota/native packages permit; x86_64 after review) with Caddy serving the static build and proxying API/WebSocket to loopback. API, worker and PostgreSQL 18 remain local to that host. Public ingress is HTTPS 443 and certificate/redirect HTTP 80 only. Keep ports 3000, 3001 and 5432 private, and restrict SSH via OCI Bastion. OCI NSG/security-list rules and host iptables are independent gates. Do not publish an AAAA record before IPv6 review. No public PostgreSQL access is permitted.

## Existing script contracts

- `deploy/provision.mjs` runs only on approved Ubuntu staging as root with `staging.<OWNED_ZONE> --approve-host-provisioning`. It installs Node 24, PostgreSQL 18 client/server, Caddy and iptables-persistent, creates distinct `ages-release`, `ages-api`, `ages-worker` and `ages-backup` Unix users, installs separate unit/env placeholders and edits host 80/443 rules. This is a mutating host operation; never run it during intake/preflight.
- `deploy/release.mjs --commit=<40-char-SHA>` prepares an immutable worktree as `ages-release` with no database change or service switch. The same SHA with `--approve-migrations` explicitly runs `prisma migrate deploy` using root-only `migrate.env`, applies grants, seeds during a short maintenance window, prepares pg-boss with worker credentials, switches the symlink and waits for readiness. `deploy/deploy.ps1` is the Windows wrapper; it fetches and selects that exact SHA in `/srv/ages/source` before executing the script. The operator first clones the reviewed source to that path after host provisioning, as specified in the runbook. Do not use an unreviewed SHA or branch tip.
- `deploy/ages-api.service` reads only `api.env` as `ages-api`; `ages-worker.service` reads only `worker.env` as `ages-worker`; `ages-backup.service` reads only `backup.env` as `ages-backup`. Root owns `/etc/ages` mode 0755; service files are 0640 root:respective-group and `migrate.env` is 0600 root:root. `/srv/ages` is writable by `ages-release` and read-only to runtimes. `/var/backups/ages` is 0700 `ages-backup`. Ensure the worker file includes its own HTTPS `APP_ORIGIN` and distinct strong `OPS_TOKEN` because production config validates both.
- A bootstrap PostgreSQL administrator privately creates `ages_migrator`, `ages_api`, `ages_worker` and read-only `ages_backup` SCRAM roles, `ages` database owned by migrator, `pgboss` schema owned by worker, and revokes public connection. Run the checked-in `deploy/database-grants.sql` only under the gated release path. Bootstrap credentials are never in any service file.
- `deploy/backup.mjs` makes a restrictive, atomic local custom-format dump and keeps seven files. `deploy/restore.mjs` accepts only an empty non-production `ages_restore_*` database with `--confirm-empty-target` and refuses a second populated-target restore. Off-host age encryption, Object Storage upload, private-key separation, retrieval and measured recovery are **operator runbook steps**, not automatic script behavior.

Before any host action, run `pnpm staging:preflight` and `pnpm staging:plan` with a completed ignored `.local/staging/intake.json`. These commands only inspect OCI metadata and DNS; neither provisions nor approves. Record the exact CI run, human approvals, approved CIDRs/shape, package provenance, native-module resolution and denied-access results in the restricted evidence store. An approved operator follows the numbered runbook for first provision, exact-commit release, migration, TLS/gameplay, WebSocket recovery, encrypted off-host backup and empty-target restore.

## Verification and recovery boundaries

Release foundation CI run [35798559620](https://github.com/KyoshiCodes/Ages-of-Ash/actions/runs/35798559620) at commit `47bc4a1` passed the disposable PostgreSQL 18.6 service/client drill: three migrations, repeat migrate/seed, native dump, empty-target restore, populated-target refusal, 29 unit, 6 integration, 5 E2E and performance. This proves hosted CI parity, **not** OCI/TLS/off-host recovery. Local Windows `pnpm verify:full` likewise exercises a disposable database and cannot validate cloud IAM, network or keys. The CI job uploads sanitized reports but excludes dumps.

`/api/live` is liveness; `/api/ready` verifies database, migrations, catalog, world and worker heartbeat. Worker `/ready`/`/metrics` and API `/internal/metrics` stay loopback/operator-only; Caddy blocks public `/internal/*`. Alert on repeated readiness loss, stale worker heartbeat, job failure/retry/lag, backup age/transfer, certificate expiry and disk pressure, then test delivery and acknowledgement. JSON journals omit secrets, URLs and player state; restrict journal readers and cap storage. Analytics defaults disabled and 30-day cleanup requires explicit action.

Code rollback can restore a prior symlink only when the database operator confirms schema/data compatibility. It never reverses migrations or data. Incompatible changes require stopped writes, a separately restored/validated database and explicit cutover approval. See [RECOVERY.md](../docs/RECOVERY.md). Actual RTO/RPO, off-host backup, key-custody separation, ARM64 binaries, alert delivery, physical-device and accessibility results remain unverified.
